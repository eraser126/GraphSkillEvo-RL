# 强化学习技能编辑器与可学习节点验证项目设计

版本 1.0　日期 2026 年 11 月 2 日

本项目拟在 GraphSkillEvo 的技能内图表示上，引入可编辑的节点检查条件，并借鉴 Skill-α 的学习范式，训练一个能够利用执行证据修改技能的 LLM 编辑器。执行任务的 agent 模型参数保持固定。系统通过多次任务执行，改进技能图的节点、路径和检查条件，同时学习能够迁移到新技能的编辑方法。

核心研究问题是：**在执行 agent 固定、执行成本可比的条件下，节点验证和图上的回溯分析，能否帮助强化学习编辑器找到更有效的修改位置与修改内容，并把这种能力迁移到未见技能。**

本文给出的是拟开展的研究设计，没有本方法的训练结果或性能结论。节点验证、轨迹对齐及其对学习的贡献，均需实验检验。

## 1 已确定的项目边界

本阶段只训练技能编辑器。技能图和 verifier 条件是被编辑的外部知识，不是单独接受梯度更新的模型；执行 agent、检查执行器和最终任务评分器保持固定。

采用 GraphSkillEvo 的语义步骤粒度：一个节点表示有明确目的、可复用的操作阶段，内部可以包含多次工具调用。图作为流程指导提供给 agent，不通过程序强制所有行为沿图执行。实际轨迹中的跳过、重访、顺序变化和图外步骤都被记录，作为潜在修改依据。

第一版在任务执行结束后进行检查汇总、回溯诊断和技能编辑，不实现运行中恢复环境、回到断点继续执行。节点检查失败不直接终止任务；缺少必要输入或工具报错导致无法继续时，按实际情况记录结束原因。

最终需要同时得到两类成果：一套训练好的、可迁移的技能编辑策略，以及一组优化后的技能图和节点检查条件。新技能适配时，允许先执行少量练习任务，但编辑器和执行 agent 的模型参数均冻结；最后使用另外的未见任务评价技能收益。

本设计不受当前远程代码实现状态约束。本次工作只形成设计文档，不启动训练或修改服务器代码。

## 2 原方法与拟议扩展

### 2.1 沿用 GraphSkillEvo 的部分

GraphSkillEvo 将 skill 组织为全局指导、可复用步骤节点，以及按适用条件选择的有序工作流。流程中相邻节点隐含有向连接；共享节点可以被多个工作流引用。它优化技能文档，执行 agent 及 harness 固定。[GraphSkillEvo 论文第 2 至 3 节](https://arxiv.org/html/2609.21749)

公开样例中的节点并不等同于一次工具调用。例如，表格技能中的工作簿检查节点包含加载、识别工作表及定位表头；ALFWorld 样例允许单节点包含多个环境动作。我们沿用这种粒度。[表格技能样例](https://github.com/ruisun7/GraphSkillEvo/blob/main/ckpt/gpt-5.4-nano/spreadsheetbench/best_skill.md)、[ALFWorld 技能样例](https://github.com/ruisun7/GraphSkillEvo/blob/main/ckpt/gpt-5.4-nano/alfworld/best_skill.md)

原方法使用自然语言指导 agent 遵循流程，不等同于硬性的图执行引擎。因此，本项目把节点执行对应关系作为需要记录和核验的信息，不假定 agent 一定遵循了图。

### 2.2 借鉴 Skill-α 的学习范式

Skill-α 固定任务执行 worker，使用 GRPO 训练 LLM 技能编辑策略，并以原技能与候选技能的受控执行比较评价编辑。本项目借鉴这一学习对象和反馈方式，将编辑目标扩展为带节点检查条件的技能内图。[Skill-α 论文第 3 至 4 节](https://arxiv.org/html/2608.01678)

这不是把两个仓库直接拼接。图补丁格式、轨迹对齐、检查条件评价和任务划分需要重新设计。GRPO 仅提供优化编辑器的方法，不保证比进化搜索更强，也不保证找到全局最优。

### 2.3 本项目新增的机制

| 维度 | 沿用的基础 | 拟增加的设计 |
|---|---|---|
| 技能表示 | 步骤节点与条件工作流 | 节点标识、检查条件、证据引用与版本记录 |
| 执行反馈 | 任务轨迹与最终结果 | 节点对齐记录、检查结果及未对齐片段 |
| 修改依据 | 执行经验 | 流程偏离、检查矛盾和疑似上游问题 |
| 学习对象 | LLM 技能编辑策略 | 同一编辑器同时学习改图和改检查条件 |
| 收益评价 | 修改前后任务表现比较 | 对检查修改经后续修复产生的收益进行评价 |

预期贡献是验证这些机制如何改善技能编辑，而不是仅把“EA 换成 RL”作为充分的新颖性依据。正式投稿前仍需系统核对相近的过程验证、技能编辑及可学习检查工作。此前讨论过的 CoSkill 当前摘要页已标记撤回，不作为本方案有效性的支撑。[CoSkill 当前状态](https://arxiv.org/abs/2609.04865)

## 3 研究问题与可检验假设

**RQ1 编辑有效性。** 同样的技能图、执行模型和预算下，学习到的编辑策略是否优于原进化搜索和未训练的 LLM 反思编辑？RL 可能更善于利用重复出现的模式，也可能因数据不足而不如简单搜索。

**RQ2 过程证据价值。** 节点检查与依赖回看是否比只有最终结果、或者只检查最后失败步骤，更有助于提出有效修改？图顺序不能自动证明因果关系，评价重点是修复位置选择及修改收益。

**RQ3 检查条件可学习性。** 编辑器能否增加必要检查、删除无用检查、调整过严或错误的条件，使后续修复更有效？检查数量、通过率和最终成功的相关性都不足以单独回答这一问题。

**RQ4 迁移能力。** 编辑器面对未见技能，利用少量练习轨迹，能否改善另外的未见任务？同时评价适配收益及适配成本，避免只展示在触发修改的原题上成功。

这些问题对应的预期是：检查提供更有用的证据，编辑器据此减少无效修改，检查条件再通过修复收益得到改进。如果效果仅来自更多调用、更多重试或更长上下文，则不支持预期机制。

## 4 系统架构

系统保留四个主要组成部分。轨迹对齐、版本管理和日志属于固定基础设施，不额外引入可训练智能体。

| 组成部分 | 职责 | 第一阶段是否训练 |
|---|---|---|
| 执行 agent | 读取技能、调用工具、完成任务 | 否 |
| 技能图 | 存放全局指导、节点内容和适用流程 | 由编辑器修改外部内容 |
| 节点 verifier | 根据节点证据和当前条件产生检查报告 | 执行器固定，条件可编辑 |
| LLM 技能编辑器 | 选择修改位置，输出图或检查条件补丁 | 是，使用 GRPO |

整体过程如下：

```text
技能图与检查条件
  → 固定 agent 执行练习任务并记录证据
  → 对齐节点并进行事后检查
  → 编辑器调整条件  重新检查并形成诊断
  → 编辑器依据新反馈修改技能图
  → 固定 agent 使用新旧技能执行对照任务
  → 外部评分比较并训练编辑器或评价适配
```

第一版采用旁路检查：检查报告进入编辑器上下文，不在当前任务中强制控制 agent。这样检查条件的价值主要体现为它能否指导下一次技能修复。若以后让检查结果直接驱动运行中纠错，需要作为新的执行设置另做对照。

## 5 技能图与检查条件表示

### 5.1 图的基本结构

每个 skill 保持自己的内部图，包含全局指导、节点列表和工作流列表。工作流包含适用条件和有序节点引用。第一版不额外要求图无环：多个流程共享节点、重复访问或恢复行为都可能产生环，合法性检查关注引用完整、路径可解释及规模有界。

节点建议保存以下字段：

| 字段 | 含义 |
|---|---|
| node_id | 稳定标识，节点改名时仍能追踪 |
| purpose | 该步骤要完成的目标 |
| instruction | 操作指导及适用限制 |
| evidence_expected | 完成该步骤通常应留下什么可观察证据 |
| checks | 当前检查条件列表，允许为空 |
| version | 节点版本及关联补丁 |

这些是本项目的扩展数据契约，不宣称原仓库已采用此格式。技能图可渲染为原风格的自然语言文档；检查专用条件和诊断报告默认在编辑通道中使用，不隐式增加执行 agent 的提示信息。若某项要求确实应指导执行，编辑器需显式把它写入节点 instruction。

### 5.2 固定接口与可编辑条件

固定接口约定检查系统接收和返回什么。输入为节点定义、实际执行片段、节点时刻的中间产物、可访问的上游证据及条件列表。输出为每条条件的状态、证据和解释。

可编辑条件决定检查什么。它不是硬编码的单题答案，而是可用于一类任务的要求，例如“数值保留单位和来源”“写入范围与请求一致”“下一步需要的字段已经齐全”。条件可以包含与 skill 领域有关的语义；泛化不要求所有条件跨所有领域通用。

建议每条条件包含：检查标识、适用情境、检查对象、判断要求、需要的证据及检查方式。编辑器可以修改这些内容，但不能修改接口、执行器模型参数或官方最终评分器。

示例条件：

```json
{
  "check_id": "numeric_unit_consistency",
  "applies_when": "输出将用于带单位的数值计算",
  "target": "节点输出的数值及来源记录",
  "requirement": "数值附有可追溯单位，跨单位计算有转换依据",
  "evidence_needed": ["提取结果", "来源片段", "转换记录"],
  "method": "rule_then_llm"
}
```

字段存在、类型、文件可读性等优先由固定程序检查；语义一致性等由固定 LLM 按条件检查。第一版不开放任意生成代码作为 checker，避免把方法验证变成检查程序合成项目。

### 5.3 检查状态

条件层面返回 pass、fail、unknown 或 not_applicable。unknown 表示证据不足或无法可靠判断；not_applicable 表示条件在当前情境不适用。节点层面另记录 executed、skipped、off_graph 或 alignment_unknown。

未执行、未对齐和没有检查条件，都不能计为“检查通过”。没有快照时，不能用任务结束后的文件状态冒充节点刚完成时的状态。空条件列表表示未覆盖，不因通过率统计而获益。

每个节点都有挂接检查的接口，但不强制每个节点始终保留若干条件。删除所有无效条件后，节点可以暂时没有检查；是否补回，由之后的执行证据及收益决定。

## 6 指导式执行与轨迹对齐

### 6.1 保留 agent 的执行灵活性

agent 阅读流程指导后可以实际发生偏离。系统记录偏离，而不预先认为偏离正确或错误。它应尽量输出简短的节点开始和结束标记，但标记仅是证据之一，不能作为执行事实的唯一依据。

对齐器结合标记、工具调用、参数、观察和中间产物，判断某段轨迹属于哪些节点。同一次工具调用可能同时服务多个节点；同一节点也可能被多次访问。保留置信程度和无法对齐片段，不强行一对一归类。

第一版优先选择可保存中间产物的任务。文件类任务可在显式阶段标记或关键写操作后保存只读快照；无法确认真实阶段边界时，记录时间范围与不确定性，不虚构节点结束时刻。

### 6.2 如何利用偏离改图

| 轨迹现象 | 可提出的修改假设 | 需要排除的解释 |
|---|---|---|
| 多次跳过节点仍成功 | 改为可选、合并或删除 | 任务太简单，或实际隐式完成 |
| 成功轨迹反复出现图外步骤 | 插入节点或补充现有指导 | 偶然行为、冗余动作、特定实例技巧 |
| 成功时顺序与流程不同 | 调整路径或增加适用流程 | 原流程在其他条件下仍必要 |
| 某步骤反复重访 | 补前置条件、改指导或增加恢复流程 | 工具波动、执行模型自身失误 |
| 跳过节点后常见失败 | 强化适用情境或说明必要性 | 任务难度混淆，并非跳过导致失败 |

这些统计用于产生候选修改，不用于自动删除节点或直接给节点评分。候选最终由受控任务表现比较检验。

### 6.3 流程关系与证据依赖

图中的先后关系表示建议流程，不自动表示数据依赖。回溯时另外记录中间产物由谁生成、被哪些后续动作读取，以及证据引用关系。可从失败节点的实际输入向上查找，也可用工作流前驱缩小候选范围。

不需要第一版构建完美的数据流图。可以使用文件路径、字段、工具输出引用及 LLM 证据分析近似建立关系，但必须标注推测。只有时间先后、没有内容证据的上游节点，不能因此被称为根因。

## 7 检查反馈与疑似问题定位

诊断同时使用成功和失败轨迹。第一版可采用固定规则汇总加固定 LLM 形成短报告，编辑器依据报告和原始证据决定修改。诊断器不是第二个训练目标。

需要覆盖四类情况：

- 最终失败且有检查失败：分析失败条件，检查当前节点及实际输入来源，避免默认只修最后一个报错点。
- 最终失败但已执行检查均通过：考虑检查覆盖不足、条件太宽松、节点之间缺少约束，或问题发生在图外片段。
- 最终成功但有检查失败：考虑条件过严、不适用、判断错误，或 agent 已自行恢复；一次成功不直接触发删除。
- 最终成功且检查通过：提炼可复用步骤，但不把所有经过的节点都判为高价值。

输出应为少量候选位置、支持证据、替代解释和建议操作。证据不足时允许不定位。术语使用“疑似根因”“可疑节点”“修复位置选择”，不声称已证明因果根因。

第一版不要求先修正节点中间输出再重放后续步骤来验证原因。可控故障实验与人工审阅用于评价候选是否合理，但不将自然失败的模型自评当作真实根因标签。

## 8 强化学习对象与编辑动作

### 8.1 训练一个 LLM 编辑器

编辑器输入为当前图、检查条件、练习轨迹和检查报告；输出结构化补丁。固定执行程序应用补丁，不让模型直接修改评测器或工具权限。

第一版建议采用以下基本操作：

| 对象 | 操作 |
|---|---|
| 节点内容 | 改写指导、插入节点、删除节点 |
| 工作流 | 调整节点引用顺序、增加或修改适用流程 |
| 检查条件 | 增加、删除、改写条件及其适用情境 |
| 任意对象 | NOOP，保留现状 |

节点合并可先表达为改写、重定向引用和删除的有限组合，不增加独立复杂算子。每次补丁限制少量变更，并包含基础版本、目标标识、证据引用和修改理由。理由用于审计，不因文字有说服力而获得奖励。

补丁应用前检查引用、字段、版本和规模；删除节点时必须处理所有相关工作流和条件引用。不合法补丁记录失败，不能悄悄截断成另一份补丁。工具超时或环境故障应重试或排除，不当作编辑能力差而给负奖励。

### 8.2 用两步编辑闭环学习检查条件

如果节点 verifier 只是记录日志，而条件不影响任何后续决策，则最终任务奖励无法有效区分好坏条件。这是方法必须解决的反馈断点。

建议最简训练单元包含同一编辑器的两次决策：

1. **检查编辑。** 读取当前图和练习记录，输出检查条件补丁或 NOOP。
2. **技能修复。** 固定检查执行器用新条件重新检查同一批不可变证据，形成新报告；同一编辑器依据报告输出图补丁或 NOOP。

随后用固定执行 agent 比较原技能与最终候选技能的实际表现，把收益作为整段编辑序列的回报。这样，检查条件通过影响第二步修复而获得间接监督。

两个阶段使用同一个可训练 LLM，只通过提示词明确当前允许的操作。首版不再训练独立的 verifier、诊断器或算子调度策略。两步设计是本项目建议的简化机制，需要验证，并非 Skill-α 已经提供的节点检查优化模块。

这类延迟回报不能精确判断每条检查的贡献，存在信用混淆。第一阶段接受这一局限，通过固定编辑器的受控实验分析条件价值，而不先引入节点级奖励模型。

### 8.3 奖励与 GRPO

主要奖励采用候选技能相对原技能的外部任务得分变化，扣除新增执行和检查成本；不合法编辑给予固定惩罚。任务分数和成本量纲需要归一化，成本权重由开发集确定并在测试前冻结。

不直接奖励检查通过率、检查数量、疑因报告自评分或成功轨迹中某节点的出现次数。否则，编辑器可能通过删光检查、放宽条件或增加模板文字获得虚假收益。

对同一初始图和练习证据，采样一组两步候选编辑序列。各候选使用同一训练奖励任务面板，与共享原技能基准比较。GRPO 依据组内相对收益更新编辑器的生成概率；两次决策的可训练输出共同接受该序列回报。

reward 面板的任务内容、答案和详细评分报告不进入候选生成上下文；仅在候选生成完成后，用于计算训练奖励。这里的“不进入上下文”并非不参与学习：标量收益仍通过梯度训练编辑器。验证集用于选择 checkpoint，最终测试不参与任何更新或选图。

原技能与候选技能应从相同初始环境、文件和可比采样设置运行。支持配对随机种子的环境尽量配对；托管模型未必完全可复现，必要时重复执行并报告方差。不得把本项目的轨迹回溯等同于恢复同一运行现场。

若组内回报没有差异，应检查任务过易、修改没有影响、评价噪声或检查反馈失效，不能把训练正常结束等同于学到了编辑能力。格式启动可以使用开发材料生成少量合规补丁做 SFT，但训练材料不包含保留评测任务或其答案。

## 9 编辑器训练与新技能适配

### 9.1 编辑器训练

以多个训练技能及其任务族构造训练单元。每个技能保留诊断任务和奖励任务两类实例：诊断任务产生可见轨迹及检查反馈；奖励任务在候选生成后评价修改，输出标量奖励。重复采样只增加执行次数，不增加独立技能数量。

每次更新前保存图版本、条件、证据快照、候选补丁、成本和外部评分。建议从固定长度的两步编辑序列开始，再考虑跨多轮的长程信用分配。训练期间产生的技能版本只是外部状态，不能与模型 checkpoint 混为一谈。

### 9.2 新技能适配

新技能进入系统后，冻结编辑器参数，按预先规定的预算执行：

1. 建立或读取初始图及初始检查条件。
2. 在少量 support 练习任务上执行固定 agent，记录证据。
3. 用冻结编辑器完成检查调整及技能修复。
4. 如允许多轮，再用新的 support 证据继续；候选选择仅使用指定的适配开发任务。
5. 冻结最终技能图和检查条件，在 query 未见任务上评价。

单个新技能如果只有一个任务实例，而没有独立的练习和测试实例，就不能完成这种迁移检验。需要补充经核验的适配任务，或将该技能只用于其他评测，不以同题重复执行替代泛化。

### 9.3 三层数据隔离

| 层次 | 隔离对象 | 防止的问题 |
|---|---|---|
| 编辑器训练与测试 | 技能包、共享组件、任务模板及近重复族 | 编辑器记住训练技能的补丁 |
| 单轮编辑与奖励 | 可见诊断证据与不可见奖励任务 | 只修好提供反馈的原题 |
| 测试时适配与报告 | support 与最终 query | 用最终测试结果反复选择技能 |

新技能实验中的 query 结果仅用于最后报告，不反馈给编辑器，也不用于挑选轮数和候选。若事后查看失败案例继续研发，则该部分从此属于开发材料，应另留未触碰任务做后续确认。

若适配时使用额外开发任务选择候选，必须单独列出实例数、访问次数和调用成本，并向各方法提供同等选择预算；不隐含一个大型验证集。最简适配可只生成一个候选，按预定轮数结束后直接冻结，无需另设选图集。

## 10 Benchmark 与数据方案

### 10.1 SkillsBench 的定位

SkillsBench 作为首个探索平台和主要评测候选。官方任务包包含技能、环境、参考解及最终验证程序；v1.1 发布说明列出 87 个任务、8 个领域。研究开始时固定 release、commit 和实际纳入清单，避免与历史版本的任务数混用。[官方任务结构](https://github.com/benchflow-ai/skillsbench)、[v1.1 发布说明](https://www.skillsbench.ai/blogs/skillsbench-1-1)

其最终验证程序与本项目节点 verifier 完全分开。官方评分器固定，参考答案、oracle 和隐藏测试不进入执行 agent、对齐器或编辑器的上下文；节点检查只使用执行者在正常任务中能够观察到的证据。

SkillsBench 是评测平台，不默认提供适合 GRPO 的标准训练集。官网有防训练污染提示，公开下载与开源代码许可也不能自动推导出可把所有任务用于权重训练。本方案默认不使用保留 SkillsBench 任务进行 SFT 或 GRPO；训练数据用途需另行核验。[SkillsBench 官网](https://www.skillsbench.ai/)

### 10.2 两条实验轨道

**开发探索轨道。** 先选取约 8 至 12 个任务，用于验证图转换、对齐、快照和检查机制。数量只是起点建议，按任务成本调整。入选条件是存在多个语义阶段、可观察中间产物、有固定最终评分，且不依赖难以复现的外部服务。这批任务一旦用于开发，就不再作为未见测试报告。

**保留评价轨道。** 提前按技能与任务族保留未使用的 SkillsBench 任务。编辑器在已核验可训练的外部材料上学习，再使用与保留 query 分离的练习实例适配新技能。练习实例应独立设计或来自其他合适来源，经过人工检查、环境验证及去重，不能从 query 答案或测试程序反推。

如果需要在 benchmark 内研究少样本适配，必须先核验使用约束，公开自定义研究划分和适配协议。结果称为“SkillsBench 上的研究适配评估”，不直接混入官方原始协议排行榜结果。

某些任务需要组合多个 skill。本项目不把它们拼成技能间图：第一版选择一个目标 skill 进行内部优化，其余技能固定。若之后同时编辑多个 skill，需明确预算分配与评测归属，另作为扩展设置。

### 10.3 补充平台

首选候选是 SpreadsheetBench。它具有真实表格操作任务及结果文件比较，适合检查读取范围、数据转换和写入位置等问题，也方便与 GraphSkillEvo 的已有任务设置建立联系。[官方仓库](https://github.com/RUCKBReasoning/SpreadsheetBench)

ALFWorld 可后续用于交互场景和前置条件分析，不作为第一版必须完成的第三平台。补充数据集不能自动视为独立：需要检查它们与 SkillsBench、技能包和生成训练材料是否共享实例、文件或模板。第一版优先完成一个主平台的可信证据链。

## 11 对照与消融实验

### 11.1 必要比较

| 编号 | 方法 | 主要回答的问题 |
|---|---|---|
| B0 | 无 skill 的固定 agent | 初始能力与技能基础收益 |
| B1 | 原始文本 skill | 原始技能参照 |
| B2 | 静态图 skill | 图表示及初始转换影响 |
| B3 | 原 GraphSkillEvo EA | 与原工作搜索方式比较 |
| B4 | 未训练的 LLM 图编辑器 | RL 是否优于提示词反思 |
| B5 | GRPO 图编辑器，无节点检查报告 | 学习编辑的基本收益 |
| B6 | GRPO 图编辑器，固定节点检查与回溯 | 过程证据的增量价值 |
| M | GRPO 编辑器，可学习检查与回溯 | 完整方法的增量价值 |

最早 demo 可先做 B2、B4、B5、B6 和 M 的机制检查；正式比较应补齐原 EA 与文本参照。基线应共享初始图、执行 agent、任务环境、工具权限和可见证据范围。未训练编辑器与训练编辑器尽量使用相同基础模型；若不同，单独报告模型因素。

B3 按原方法保留其搜索流程，在统一任务适配器上运行并报告修改点。不能给 EA 更少的真实评估预算，再把差异归因于 RL；也不能只比较编辑器调用次数而忽略候选技能执行成本。

所有编辑基线都能访问相同的原始 support 轨迹、阶段标记和证据快照；节点检查与回溯报告才是需要控制的实验变量，不能通过少给基线原始证据制造优势。原 EA 若需扩展证据输入，应同时保留原设置结果，并将该扩展明确标为适配版本。

### 11.2 机制消融

**回溯价值。** 保持检查报告和上下文预算相近，比较只关注末端失败节点、使用完整执行记录反思，以及加入流程与证据依赖回看。进一步打乱图连接但保留节点内容，检查效果是否真的依赖结构。

**表示价值。** 使用相同节点指导和检查条件，将图渲染成有路径引用的形式，或平铺清单。控制内容、提示长度与调用预算，避免把信息更多误认作图结构更好。

**检查可学习性。** 比较固定初始条件、未训练 LLM 修改条件、RL 学到的条件。除端到端比较，还固定同一个图修复编辑器、同一批 support 证据、同一修复预算，只替换旧条件和新条件，观察后续修复收益。这个实验尤其重要，因为检查补丁和图补丁共享最终奖励，端到端提升不能独立证明检查修改有效。

**偏离证据价值。** 移除跳过统计或图外片段报告，观察节点删除、插入及路径调整的有效性变化。频率本身不作为真实性标签。

**迁移价值。** 分别评价同技能未见实例、未见技能、未见领域。第一版必须完成前两项；跨领域与跨执行模型为加强实验，不在数据不足时强行外推。

### 11.3 预算公平性

同时报告每任务成功率和成功率随累计调用成本的曲线。成本包含编辑、检查、对齐、诊断、候选执行、失败调用和初始化；外部服务价格变化时保留原始 token 及调用数。

分别报告编辑器一次性训练成本和新技能适配成本。前者不能在比较部署时被隐去，也不应全部重复计到每个新任务上。给出在不同技能数量下摊销的结果，避免只用一个口径得出效率结论。

## 12 指标与分析方法

### 12.1 任务与适配结果

主要指标为官方任务成功率、相对初始技能的配对增益、每技能适配收益，以及累计成本下的收益。尽可能报告多次编辑训练种子与执行重复；重复次数由预实验成本决定并在正式测试前固定。

统计单位优先是独立任务族或技能组，同一任务多次 seed 不当作多个独立任务。使用按技能组聚类的 bootstrap 估计区间，辅以每组结果和失败案例。样本过少时重点报告效应大小及不确定性，不强求显著性。

### 12.2 图与检查行为

记录对齐覆盖率、未确定比例、跳过与重访分布、图外片段、节点及路径变化、补丁合法率、候选修改收益和图规模。检查方面记录触发、通过、失败、unknown、未覆盖及成本，但不把高通过率当作质量指标。

另记录编辑器是否引用新检查的具体证据，以及替换新旧条件后修复补丁是否改变。结合固定编辑器对照，检查模型是否真正利用了 verifier，而不是忽略报告、仅靠原轨迹完成修改；引用本身仍不作为奖励或有效性的充分证明。

检查质量另用人工审阅的小规模轨迹集评价：检查是否有证据依据、是否误报、是否遗漏实际可观察问题。只有存在人工或可执行局部正确性标签时，才报告准确率、精确率和召回率；不能拿最终任务成败代替每个节点的正确性标签。

### 12.3 定位与修复

自然失败中，报告候选位置的人工合理性、修改有效率和未见实例收益。可控故障实验可插入缺失步骤、错误指导、错误流程引用及过严或过松检查，记录 Top-k 候选命中与修复收益。

故障来源标签只提供给评价程序，不提供给编辑器。每个注入故障需先确认确实影响对应任务；注入位置只是已知改坏位置，不自动等于自然失败的真实因果根因。合成故障与自然失败结果分开报告。

## 13 一个完整的预期案例

初始技能包含读取资料、提取数据、计算、生成报告四个节点。数据提取节点只检查“需要的数值是否齐全”。某练习任务中该检查通过，但最终计算结果错误。

回看节点快照发现，两项输入使用不同单位。编辑器在第一步增加“保留来源单位并检查兼容性”的条件。固定执行器重检原快照，返回单位不兼容的证据，而不是把计算节点简单标成失败根因。

第二步编辑器改写数据提取指导，要求记录单位，并根据多条轨迹决定把标准化作为独立节点，还是补入现有节点。若成功轨迹常有独立转换步骤，插入节点成为一个候选；仍需执行验证，不凭出现次数直接接受。

新旧技能在同一批独立对照任务上运行。只有修复带来外部任务收益或减少成本，整段编辑序列才获得相应回报。若新增检查误报很多，后续候选可以限定其适用条件或删除它。

最终保留技能用于另一批 query 任务。这里描述的是方法应能展示的行为案例，不是已经得到的实验结果。

## 14 探索阶段与退出条件

### 14.1 阶段一 检查与对齐是否可用

先用 SkillsBench 开发任务验证语义节点、执行标记、快照、图外片段及检查报告。人工审阅一小批成功和失败轨迹，判断是否能区分真实跳过、隐式执行和不确定对应。

交付为固定初始技能、轨迹与产物快照、节点对齐记录、初始检查条件和人工审阅记录。若证据不足导致大量 unknown，应先改证据记录或缩小任务类型，不急于训练编辑器。

### 14.2 阶段二 检查是否帮助修复

暂用未训练 LLM 编辑器，比较无检查、固定检查、可编辑检查的两步闭环。覆盖“失败且检查全过”“成功但检查失败”“成功图外步骤”和“上游输入问题”几类案例。

这一阶段不用于证明 RL 优势。若新的检查报告不能稳定改变修复行为，或者修改条件只改变日志而不影响候选，就不进入大规模 GRPO，应先修复反馈链。

### 14.3 阶段三 训练编辑策略

使用核验过的训练材料，接入两步 GRPO。先验证可获得非零奖励差异、格式有效输出和稳定的训练数据记录，再逐步增加任务族。模型规模、上下文、候选组大小和 LoRA 设置依据实际资源确定，不预设大模型训练为必要条件。

可先尝试每组 4 个候选、每候选两次编辑决策、少量诊断及奖励实例。数值仅为探索起点，不是复现配置或功效保证；正式设置需依据奖励方差和调用成本冻结。

### 14.4 阶段四 评价泛化与机制

冻结 checkpoint 和超参数，进行新技能 support 适配及 query 评价。完成核心基线、固定图编辑器的检查替换实验，以及自然失败和可控故障分析。

最低可支持的结论是：方法能在明确范围内利用节点证据产生更有效的修改。若 RL 没有优于未训练反思，或可学习检查没有优于固定检查，应如实缩小主张，分析数据量、奖励噪声与成本，不以增加模块替代证据。

## 15 风险与设计应对

| 风险 | 表现 | 优先应对 |
|---|---|---|
| 对齐错误 | 把隐式执行认成跳过 | 保留unknown，人工抽查，结合工具与产物 |
| 检查自我放宽 | 通过率升高但任务未改善 | 不奖励通过率，保持外部评分固定 |
| 延迟收益混淆 | 图修复有效但检查修改无用 | 固定图编辑器做检查替换对照 |
| 流程被误作因果 | 总把上一个节点判为根因 | 区分实际证据依赖，只输出疑因 |
| 技能或条件过拟合 | 只修好原题 | 隔离诊断、奖励、query及技能族 |
| 图与检查膨胀 | 增加大量节点和条件 | 规模上限、NOOP与删除、计入总成本 |
| 数据量不足 | 大量轨迹但只有少数独立技能 | 扩充独立任务族，先做机制验证 |
| 训练与评测污染 | 测试报告回流修改 | 固定划分、访问日志和一次性保留评价 |

## 16 拟形成的贡献与交付物

方法贡献拟集中在：面向固定执行 agent 的检查增强技能内图编辑；利用实际轨迹与图的偏离及节点证据提出修复；通过后续修复收益学习检查条件。贡献是否成立，以对照实验为准。

交付物包括可训练与可部署的编辑器、版本化技能图及检查条件、对齐轨迹和证据快照、可审计补丁记录，以及按技能组隔离的评价协议。展示案例应同时包含有效修改和失败修改，而不只挑选成功故事。

工作题目可暂用“基于节点验证与执行回溯的技能内图强化学习优化”。正式论文标题与创新性主张在结果形成、相近工作核对后再确定。现阶段下一步是先完成少量任务的证据记录与两步编辑闭环验证。
